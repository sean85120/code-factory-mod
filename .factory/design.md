# Design

## Overview

code-factory is a Claude Code plugin (single hooks module, `hooks/register.tsx` + pure logic in `hooks/lib.ts`) that runs a design-first autonomous build loop. This factory run improves code-factory itself: it adds CI and branch protection, a real README, and closes guard bypasses found in an audit of the Bash/Agent/state guards.

Users: the owner (sean85120) running the plugin on private repos.

## Non-goals

- No new loop features, no UI changes, no changes to the slash-command surface.
- No release / tag, no plugin.json version bump.
- No standalone build, bundler, package.json or lockfile.
- The Bash guard stays best-effort, not a sandbox; the goal is closing the concrete bypasses below, not proving the guard complete.
- Audit finding F12 (lock race, `#` comments, pathspec checkout, here-string heredoc, `~~~` fences, CRLF, `git -C`, git aliases) and F8 (state-file Bash holes) are out of scope for this run.

## Architecture (unchanged)

- `hooks/lib.ts`: pure logic, every testable function and prompt string. New logic goes here.
- `hooks/register.tsx`: engine glue; one file; one handler per event unless a matcher is used (fold new tool coverage into existing handlers).
- `types/index.d.ts`: self-contained `$.state` contract.
- Tests: `tests/*.test.ts` import `claude-code/testing` and exercise `lib.ts` directly. `claude plugin test .` runs all (~3s).
- `.claude-plugin/types/` is generated by the runtime and not checked in, so `tsc` is not part of testCmd or CI.

## Version plan

- 0.2.0 infra: CI workflow, branch protection, README.
- 0.3.0 hardening: guard bypass fixes F1-F7, F9-F11 from the audit.
- The loop stops after 0.3.0. No GitHub release.
- PR #3 (add-loop-view) is merged by the person before the loop starts.

## Verification

- testCmd: `claude plugin test . && claude plugin validate .` (validate prints warnings and exits 0).
- No buildCmd (nothing to build), no e2eCmd (no app/UI), `e2eFor` empty. Behavior is covered by lib.ts unit tests and register.tsx hook tests using the test mock.
- Bug items must change tests (requireTestChanges); chore/docs items are exempt from that gate.
- Hardening items are test-first: add the failing reproduction from the item's `tests:` list, then fix.

## CI and branch protection

- No CI exists today; T-001 creates `.github/workflows/ci.yml` (job named `test`) on pull_request and push to main.
- allowNoCI stays false. The workflow triggers on the PR that adds it, so T-001 itself has checks.
- Branch protection is not enabled and the repo is private. T-002 sets it up with `gh` (PR required, `test` check required, no force push, enforce admins). requireBranchProtection stays false because the loop's own guard denies `gh api` writes to refs; T-002 is expected to be blocked if the guard denies it, in which case it records the exact command in its blocked note for the person to run by hand.

## Review

The loop reviews each branch with `/review-fix` in a fresh independent agent, up to 5 rounds, until zero danger and zero medium findings.

## Git

Base `main`, squash merge, branches `factory/<id>-*`, context `/clear` between items. Blocked or infeasible items are marked blocked and the loop continues with the next.

## Decisions

1. Scope. Options: CI + protection, README, new features, hardening. Choice: CI + branch protection, real README, bug fixes/hardening. Why: the person wants the plugin safe to run unattended before adding features.
2. PR #3 (add-loop-view). Options: person merges first / loop ignores / fold in. Choice: person merges first. Why: guards forbid non-`factory/*` branches; avoids stacked PRs.
3. CI runner. Options: install CLI in Actions / plus tsc / self-hosted. Choice: ubuntu-latest, `npm i -g @anthropic-ai/claude-code`, then `claude plugin test .` and `claude plugin validate .`. Why: only way to run the runtime-provided test kit; tsc rejected because `.claude-plugin/types` is generated, not checked in. Pitfall: if the CLI needs auth in CI, T-001 is blocked and, with allowNoCI false, later merges block too; the person must resolve it.
4. Hardening method. Options: model audits and person picks / person names / skip. Choice: audit then pick. A read-only agent audit produced findings F1-F12 (reproduced against a scratch copy of lib.ts, not independently re-run by the designer); the person picked F1-F7(F5/F6 combined), F9, F10+F11 and declined F8 and F12. Why: person's own bug list was not available; the loop re-verifies each finding with a failing test first.
5. Branch protection. Options: item via gh / by hand / make repo public. Choice: item via gh. Why: automation preferred; accepted risk that the guard blocks it (see CI section).
6. Versions. Options: 0.2.0 infra + 0.3.0 hardening stop at 0.3.0 / single 0.2.0 / stop at 0.2.0. Choice: first. Why: infra gates the hardening PRs; stop after hardening.
7. Release. Choice: no release, tagRelease false. Why: plugin is installed from the repo; no consumers need tags.
8. Verification commands. Options: test+validate / add tsc build / test only. Choice: testCmd runs both; no build, no e2e. Why: no build step or UI; tsc not runnable in CI.
9. Merge method and context. Choice: squash, clear. Why: matches PRs #1 and #2.
10. Review command. Choice: `/review-fix` (default), max 5 rounds.
11. On blocked or infeasible: mark blocked, continue with next item (default).
12. Hardening order. The hardening items all edit `hooks/lib.ts`, so they are chained with `depends:` to avoid merge conflicts.

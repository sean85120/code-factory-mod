# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`code-factory` is a Claude Code **plugin** (manifest: `.claude-plugin/plugin.json`) that ships a single TypeScript hook module (`hooks/hooks.json` → `./register.tsx`). It implements a design-first autonomous build loop: the person is interviewed once (`/factory-design`), approves the result (`/factory-approve`, which starts the loop itself), then `/factory-start` (also what approve calls) drives the model through every todo item, branch by branch and PR by PR, until CI-green merge. When the plan is done it interviews the person about the next phase (`/factory-roadmap`). Along the way it records what each item cost (`/factory-costs`) and an event timeline (`/factory-log`), and the person steers with `/factory-status`, `/factory-dashboard` (the control panel), `/factory-doctor` (readiness checks), `/factory-pause`, `/factory-stop`, `/factory-skip` and `/factory-retry`.

## Commands

```
claude plugin test .                 # every tests/*.test.ts, a few seconds; takes only the dir, no per-file filter
claude plugin validate .             # manifest + hooks/calls check
```

CI (`.github/workflows/ci.yml`, pull requests and pushes to `main`) installs `@anthropic-ai/claude-code` pinned to the version the suite was last verified on and runs those two commands; both work in a fresh clone with no login. It does not run `tsc -p .`, because the types it needs are generated by a live Claude Code session and are not in a fresh checkout. Run `tsc -p .` locally before pushing. Bump the pinned CLI version in the workflow when the test API changes.

`validate` warns that the root `CLAUDE.md` is not shipped as plugin context; that is expected, the file is for working on this repo. There is no `package.json`, bundler or lockfile. Types (`claude-code`, `EngineInterface`, `Register`) and the test runner (`claude-code/testing`) come from the Claude Code mod runtime, and `tsconfig.json` extends `.claude-plugin/types/tsconfig.json`, which the runtime generates once the mod has loaded (not checked in); after that `tsc -p .` type-checks. The plugin hot-reloads in a session, or load it with `claude --plugin-dir <path>`.

## Architecture

Source is split on purpose:

- `hooks/lib.ts`: **pure logic only**, no engine calls. Parsing and validation of `.factory/todo.md` and `settings.json`, the decisions hash, Bash command classification (`classifyBash`), PR/CI/branch-protection verdicts, test-weakening detection, lock semantics, review-marker parsing, the spend ledger arithmetic (`repoKey`, `costDelta`, `settleCost`, `addTokens`, `liveSpend`, `costsReport`), the timeline (`appendEvent`, `mergeEvents`, `formatLog`, `ciOutcome`, `parsePrUrl`), `statusReport`, the next-phase decision (`shouldAskRoadmap`), and every prompt string (`DESIGN_PROMPT`, `workPrompt`, `nudgePrompt`, `reviewAgentPrompt`, `releasePrompt`, `roadmapPrompt`). Everything testable lives here.
- `hooks/register.tsx`: the engine glue (`$` = `EngineInterface`). Registers the `/factory-*` slash commands, the loop driver, the guard hooks, and the live band. It must stay one file: a plugin has exactly one hooks module, `$` cannot be passed into functions imported from another file, and the same event cannot be registered twice without a matcher (fold new behavior into the existing handler). Module-level flags (`isFactoryTurn`, `isArmed`, `isAdvancing`) are in-memory; a reload only costs one `/factory-start`.
- `types/index.d.ts`: the `$.state` contract (`code-factory.view`) and the view types. It must be self-contained (no imports); `lib.ts` imports its types from here.

### Loop view (the band above the prompt, the status line and the dashboard pane)

`buildView` (lib.ts) turns the effective items, state and blocked set into a `FactoryView`: the stage pipeline (`build → review → PR → CI → merge`) and, for the current item, `steps` (one per stage with `done|doing|todo` and a detail: commits and attempt, review round or verdict, PR number, CI result, `itemSteps`, derived from the timeline events since the item's last `started`), open todo rows (done ones collapse to a count), `total` and `blockedCount`, `attempt`/`reviewRound` against their maxima, `prNumber`, `elapsedMs` since `started`, the last three status changes, the last three timeline events, the spend of this run and of the current item (`runUsd`/`itemUsd`, from `liveSpend`, so the unsettled part of the running turn is included; `null` when the session has no cost ledger) against `budgetUsd`, and `agents` (at most `MAX_VIEW_AGENTS`). `refreshOnce` builds it every 2 s, on `turn.complete`, and from `/factory-status` and `refreshStatus`, stores it in `$.state` (`code-factory.view`) and, only when its text changed, sets the status line below the prompt from `statusLine(view)` (item and stage bar, attempt and review round, `done/total` with a bar, what is left, blocked count, run spend against the budget with a bar, number of active agents, elapsed time; a pause reason is cut to one line). The `ui.render` hooks only read the view: the band (`AbovePrompt`: header with progress bars and a `[panel]` button, the step row, todo rows, one button per agent), and the dashboard `Pane` (`/factory-dashboard`, `requestId` `factory`: plan bar, every step with its detail, spend bar, the agent list, recent events). `agents` come from `collectAgents`: the main loop while a factory turn runs, and `$.agent.list()` (active ones first, then the last two finished ones, cached once finished); each row has a one-line `summary` and the last five actions (`agentActions`, read from `$.session.messages({ agentId })`: tool name plus its command, path or pattern, or the first line of prose). `runControls(view)`/`controlsFor(view)` (lib.ts) decide the buttons: `[⏸ pause] [■ stop]` while the loop runs, `[▶ start]` when it does not, and `[↻ retry <ID>]` per blocked row. The dashboard pane is the control panel: those buttons at the top, `[✔ check setup]` (runs `doctorChecks`, stored in the `checks` atom and also printed by `/factory-doctor`: settings, todo, approval, `gh` login, origin, design files on the base branch, clean tree, lock, readable budget), a `[skip]` button on todo rows that opens an `Input` for the reason (`skipTarget` atom; a surface without `Input` skips with no reason), and a Blocked section with each note's first line (`FactoryView.blocked`, from `blockedNotes`) and a retry button. A press runs `startCmd`/`pauseCmd`/`stopCmd`/`retryCmd`/`skipCmd`/`doctorCmd`, the same top-level functions the slash commands call, because `$.command.run` skips the calling plugin's own `command.run` hooks. A direct call skips the queueing a typed non-`immediate` command gets behind the person's running turn, so `[▶ start]` is refused while `mainTurnOpen` (set on `turn.start`, cleared on a main `turn.complete`) is true and no factory turn is running; pause and stop only ever stop things. The band narrower than 90 columns (`isCompact(e.props.bodyColumns)`) drops spend, the step row, events and changes and shows two todo rows and two agents. Pressing an agent (in the band or the pane) toggles the `code-factory.openAgent` atom and opens the pane, which expands that agent to its recent actions. A failing roster or transcript read degrades to no agents. The stage is advanced by `markStage` from the Bash hook (commit, `gh pr create`, `gh pr merge`, only when the guard did not deny) and the review Agent hook, which also moves the `steps` states; it resets to `build` when `current` changes.

Tests in `tests/*.test.ts` import `claude-code/testing` and exercise `lib.ts` directly (`gates`, `guards`, `lib*`, `safety`, `view`, `handback`, `costs`, `timeline`, `dashboard`) or drive the hooks through mocked engine ops (`control` mocks `session.usage`, `session.id`, `mock.store`, the file system and `process.run`). Engine ops the older tests do not mock (`$.store`, `$.session.usage`, `$.session.id`, `$.session.cwd`) are always called inside `try/catch` and degrade to "no spend recorded". New logic should go into `lib.ts` so it stays testable.

### The loop (register.tsx)

`advance()` is the single step function (it skips while `isFactoryTurn` is set, with a 3 h time limit so a turn that never ends cannot stall the loop for good). It is triggered by `turn.complete` (after 800 ms), by `/factory-start`, by a session starting with autopilot on, and by a 5-minute watchdog. Each call: load state → take the lock → check integrity → check the budget (`budgetReached` on this run's spend, unsettled part included; pauses with `budgetPauseReason`) → inspect the current item (marked done in todo.md **and** a merged `factory/<id>-*` PR exists, else re-send a `nudgePrompt`, blocked after `maxAttempts`) → pick the next item (`pickNext`: status `todo`, not blocked, in version scope, dependencies done) → optionally reset context (`/clear` or `/compact`) → `submit()` the work prompt. When nothing is left it optionally has the model cut a release (`tagRelease`) and pauses; then, if `shouldAskRoadmap` (setting `askNextPhase`, plan approved, every effective item `done` so nothing todo/proposed/blocked is left, `state.roadmapAsked` not set) and no other session holds the lock, it sets `roadmapAsked` and submits the next-phase interview (see below). Every `submit()` is preceded by `drive()`, which opens the spend mark for that item or phase.

`/factory-approve` starts the loop by calling `startCmd` after it writes the approval, unless the loop is already running (a second `startCmd` would open a new ledger run and reset the budget) or no item is `todo` (approving a finished plan must not trigger the next-phase interview at once); the reply carries `startCmd`'s own text, so a refused start (another session holds the lock, nothing pickable) is shown, not hidden. `startCmd` ends by calling `openDashboard`, which opens the `factory` pane without `focus` (the keyboard stays in the prompt, so typing still works) and toasts the reason when the pane is placed nowhere (a narrow terminal). Only a start the person asked for opens it (a typed `/factory-start`, `/factory-approve`, or a button press); `advance`, `refreshOnce` and a resumed session never open it, so a pane the person closed stays closed. The person leaves dashboard mode with the pane's `[close]` button, `/factory-dashboard off` (`immediate`, so it works mid-turn) or the engine's close mark (ctrl+x x); Esc does not close it (the pane has no `closeOnEscape` and never holds the keyboard) and over a running turn interrupts that turn, which pauses the loop. No `ui.close` hook is registered, so a close is never refused.

Any prompt the person types themselves, or an aborted/non-`answer` turn, pauses the loop (a prompt typed in a session whose repo lock is held by another session does not pause that loop; it sets the in-memory `handsOff` flag so this session's `advance()` and watchdog never take the loop over, even if that lock then goes stale, until `/factory-start` clears it once it holds the lock (the person gets a toast when the flag is set; a refused start leaves it set); `/factory-pause` and `/factory-stop` work across sessions). `/factory-start` also runs when nothing is pickable but a release is pending (`releasePending`) or the next-phase interview is still due (`shouldAskRoadmap`), so a halt between the last merge and the finish step (run limit, an interrupted release turn, a release that failed three times) can be resumed.

`advance()` never writes the snapshot it loaded at its top. It captures a `LoopGuard` before its `load()` (the in-memory `loopEpoch`, bumped by every person-initiated `pause()`, `/factory-start`, `/factory-stop` and a successful `/factory-approve`; `/factory-stop` and `/factory-pause` bump it synchronously as their first step, before any await), and every state write goes through `patchState` with `applyChanges(fresh, snapshot, next)` (only the fields advance changed, events merged, `mergedIds` unioned) and only if `loopLive` still holds on the fresh state (checked right after `acquireLock` too): same epoch, `autopilot` on, state readable, and this session owns the lock, with the epoch checked again after the state and lock reads (a stop that lands during them makes it false even though the lock is still owned). (A separate `pausedReason` comparison was dropped: every way to change it while `autopilot` stays on also bumps the epoch.) Its own pauses (`halt`, the billing pause) pass the guard to `pause()`, whose single check runs inside the `patchState` callback, so a stale guarded pause writes nothing, settles nothing and does not release the lock or toast. When the current item is verified merged or runs out of attempts, advance first writes the new state (item done or blocked, `current` cleared) through the same guarded `write()`, and only after that succeeds writes the blocked note, toasts and notes the outcome (`merged` with the run item count, or `blocked`) in the ledger; a pause or stop that landed while it waited on `git`/`gh`/the CI billing look-up therefore leaves no blocked note and no ledger outcome, the item and its attempts are kept, and a re-armed or restarted advance cannot apply them twice because `current` is already cleared once they are written. It re-checks `loopLive` before a context reset, before `drive()` (so no attempt is noted in the ledger) and again before `submit()` (closing a mark it just opened), each followed by a synchronous epoch check right before the `drive()`/`submit()` call, so a stop or pause fired from inside any of those awaited reads sends no prompt and leaves no open mark. So a `/factory-pause`, `/factory-stop`, `/factory-start` or `/factory-approve` (all run concurrently with hooks) that lands while advance waits on `gh`, `git` or the budget check wins: nothing is written over it, no prompt is sent, and a released lock stays released. An aborted advance that took the lock releases it (and the heartbeat) when the fresh state is not running (`autopilot` off or unreadable), so a stop that lands between its `load()` and `acquireLock` cannot leave the lock owned. An advance that stopped for that reason (`aborted`) re-arms itself once with the 300 ms timer, at most `MAX_REARMS` = 3 times in a row (reset by any advance that ends without aborting), because `/factory-start`'s own timer may have fired while the stale advance still held `isAdvancing`; the re-armed advance goes through `isAdvancing` and `turnBusy`, so it never double-submits. The finished path captures the epoch after its write and passes it to `startRoadmap`, which re-checks it before and after each await (ledger read, `roadmapAsked` write, `drive()`; a cancelled launch leaves `roadmapAsked` set, so only `/factory-roadmap` or a successful `/factory-approve` re-arms the interview) and synchronously before `submit()` (the clock read is hoisted above that check; the `roadmap` timeline event is logged after the submit; a typed prompt in that window does not bump the epoch, accepted), so a `/factory-stop` or `/factory-pause` landing during the `/clear` or any of those steps cancels the interview (the `/factory-roadmap` launch timer passes the epoch captured after its own `pause()`). `pause()` builds from the fresh state the same way: it applies only its own changes (`autopilot: false`, `pausedReason`, its event, `override`), so `current`, `attempts`, `mergedIds`, `approvedDone`, the review fields, `roadmapAsked` and events written concurrently survive; it settles the spend mark after the write.

### State and trust model (all under `.factory/`)

- `todo.md`, `design.md`, `settings.json`: written by the design interview and must be on the base branch, because the loop returns to the base branch between items and files that exist only on a `factory/*` branch vanish (which pauses the loop with "settings.json is missing"). `/factory-approve` fetches `origin/<base>` (only when `baseBranch` passes `isSafeBranchName`; otherwise it runs no `git fetch` and no `gh api` protection call at all, because a name such as `+refs/heads/*:refs/heads/*` is a refspec that would force-overwrite local branches, and refuses with the settings problem and `unsafeBaseNote`) and compares all three there with the working tree (via `git show`; `todo.md` compared after `promoteProposed`, so approve's own proposed to todo flip does not count as a difference). Any that are missing or differ make approve refuse; the refusal (`designPushSteps(base, currentBranch)`) gives the person the exact commands, to run from the repo root with nothing else staged: one command line `git checkout '<base>' && git add -- <paths> && git commit -m "Code factory design" -- <paths> && git push origin '<base>'`, and, when they are on another branch, an alternative line before it for files committed there that also runs `git checkout '<that branch>' -- <paths>` after the first checkout (when that branch's name fails `isSafeBranchName` the alternative is left out and one comment line says to copy the files over by hand). Every printed line is paste-safe as a block: explanations (which line to run, a PR instead if the base is protected, `/factory-approve` again) are `#` comment lines made of fixed text only, never a branch name or a shell metacharacter, because macOS's interactive zsh has `interactive_comments` off and runs a pasted `# ...` line as a command (an accepted name such as `x>zzt` or `x;reboot` in a comment would redirect or run); no command line carries prose or an unquoted parenthesis, and each line is one `&&` chain, so a failed checkout, add or commit never reaches its push. A last alternative, `git checkout '<base>' && git push origin '<base>'`, covers design files already committed on the base branch but not pushed (there `git commit -- <paths>` exits 1 with nothing to commit, so the other lines stop before their push). Branch names appear only single-quoted inside command lines (sound because `isSafeBranchName` rejects `'`), and when `baseBranch` fails `isSafeBranchName` no git line is printed at all and the name is not echoed (`unsafeBaseNote`: fix `baseBranch` in settings.json first); `roadmapPrompt` reuses the same steps. The factory never commits or pushes the design itself. The base branch name must pass `isSafeBranchName`, which rejects only what is unsafe in a single-quoted shell command or invalid for git, plus anything the text cleaner would change (`stripControls(name) !== name`, so a printed block is identical before and after `safeLines` and the name the person sees is the name git gets): empty, over 200 characters, whitespace, soft hyphen, U+061C, U+180E, U+2060-U+2064, U+FEFF, tag characters U+E0000-U+E007F, C0/DEL/C1 control characters, zero-width (U+200B-U+200F) and bidi override or isolate characters (U+202A-U+202E, U+2066-U+2069), quotes, backtick, backslash, `$`, `~ ^ : ? * [`, a leading `-` `+` `/` `.` (a leading `+` would make `git push origin '+main'` a force push; `+` inside a name, as in `release+x`, is fine), a trailing `/` `.`, `.lock`, `..`, `@{`, a lone `@`, `//`, `/.` and `HEAD`. Names such as `release+x`, `foo@bar` and `feature/a,b` pass and are printed single-quoted.
- `state.json`, `lock.json`, `blocked/`, `evidence/`: runtime files, auto-gitignored by `ensureGitignore`. `/factory-design`, `/factory-start` (after it holds the lock) and `/factory-approve` all run `ensureGitignore` (a failed write is swallowed), so a fresh clone or worktree hides the runtime files even though `.factory/.gitignore` is not among the pushed design files. The model is denied from writing `state.json`/`lock.json` (Edit/Write deny + `touchesFactoryState` Bash check); only the `/factory-*` commands and the factory's hooks do. `state.json` also holds the timeline (`events`, capped at `MAX_EVENTS` = 200) and the `roadmapAsked` marker, so both are covered by the same denial. Because several hooks write `state.json` from snapshots read earlier, `writeState` merges `events` with what is on disk (`mergeEvents`, keyed by ts/kind/item/detail) so a stale write never drops an event, and hook-side read-modify-writes (event logging, review verdicts, the review launch, `/factory-retry`) go through `patchState`, a promise chain that reads fresh and writes immediately. `readState` distinguishes a clean absent file (`fs.exists` false: the defaults are legitimate) from one that exists but whose read throws or is not a valid JSON object; it retries those up to `STATE_READS` = 3 times in a row. If all three fail it fails closed: it returns a state flagged `unreadable` that is approved and on autopilot (so every guard applies and commit/push/PR/merge are denied by `integrityProblem`, which reports it first), `/factory-start` and `/factory-approve` refuse, and `writeState` never writes a state flagged `unreadable`, so `patchState` (which only writes what was built from a clean read or a clean absent) can never persist defaults over the real file. For display it counts as paused, never running (`buildView`, `statusReport`, the status line), and a new session does not toast "resuming" for it. A live `advance()` that loads it toasts the reason once (`unreadableToasted`, reset when advance next loads a readable state), releases this session's lock and heartbeat, refreshes the status and returns without re-arming; it does not take the lock. The guards stay fail-closed. Recovery is fixing or deleting the file, then `/factory-start` or `/factory-approve`. The person fixes or deletes the file.
- `decisionsHash` (settings + every non-`proposed` item's id/type/title/how/accept/tests/depends/version, **not** status) is stored at `/factory-approve`. If it changes, the loop pauses until re-approved. This is what stops the model editing its own decisions.
- `done` in todo.md is only trusted if the person approved it as done (`approvedDone`) or the factory verified a merged PR (`mergedIds`); `effectiveItems` demotes anything else back to `todo`.
- Items the model discovers are appended as `status: proposed`; `/factory-approve` promotes them.
- One session per repo runs the loop: `lock.json` with a 30 s heartbeat and 2 min TTL. The heartbeat releases the lock instead of renewing it when `state.json` is readable and `autopilot` is off (a loop paused or stopped from another session), so a stale owner cannot block `/factory-start`, skip, retry or roadmap elsewhere.
- `<!-- -->` comments and fenced code in todo.md are blanked by `stripNoise` (line count preserved) so template examples aren't parsed as items. Item headings must match `## T-001 [feature|bug|chore|docs] Title`; other `##` lines are reported by `todoHeadingProblems`.

### Guards (the `tool.call` hooks)

The Bash hook is the enforcement point and is **best-effort, not a sandbox** (`splitCommands` is a tokenizer, not a shell parser: it carries an open quote across lines (falling back to line-by-line reading when a quote is still open at the end), treats `#` at the start of a token as a comment, honours `\"` inside double quotes and backslash-newline continuations (joined inside the scan, so a comment ending in `\` does not eat the next line), strips leading `if|then|else|elif|do|while|until|!`, splits at backticks and re-scans `$(...)`/backtick bodies found outside single quotes (not nested deeper than 8), and detects heredocs only outside quotes (or inside a `$(`/backtick span of a double-quoted string), so a `"$(cat <<'EOF' ... EOF\n)"` commit message does not hide the commands after it, skips heredoc bodies, and does not see through `bash -c`/`eval`, `xargs`, absolute-path `git`/`gh`, `gh api graphql`, or commands that delete `.factory/` itself, all accepted limits). Several `gh pr merge` commands or selectors in one command leave the selector ambiguous, so `gh pr view` fails and the merge is denied. It does not cover the spend ledger in `$.store` (outside the repo), so the budget is advisory against a misbehaving model (accepted limit). While the loop is live (`autopilot || isArmed`, approved, lock not held elsewhere) it blocks: pushes/commits on the base branch, force pushes, `gh api` writes to PRs/refs/contents, `-R/--repo` (read from the command's tokens by `isRepoFlag`: `-R`, `-Rx/y`, clusters such as `-sRx/y`, `--repo`, `--repo=`; `gh api` short-flag clusters and `-X=PUT` are parsed the same way), and PR creation unless the branch is `factory/*` and the gates pass in order: test files changed, no test weakening (`testWeakening` on `git diff -U0`), clean independent review for the current HEAD, build, full tests, e2e. `gh pr merge` requires a `factory/*` PR that is open, non-conflicting, with all checks green (`checksVerdict`), the head equal to the reviewed SHA, and no weakened tests; `--admin` and `--auto` are denied. A CI look-up (`gh pr checks`, `gh run view|watch|list`) joined to a gated command with `;`, `&&` or `|` does not take the look-up's early path: the gates apply to the whole command. CI failures are scanned for GitHub billing messages (`isBillingProblem`), which pause the whole loop instead of retrying. Every deny any `tool.call` hook returns is built by `deny()` (lib.ts), which runs the text through `safeLines`, so repo- or tool-controlled fragments in it (an integrity problem quoting `baseBranch`, the branch name, build/test/e2e output tails, check names in `checksVerdict`'s reason, `gh pr view` stderr, weakened test file names) reach the transcript without escape sequences, C1 or bidi controls; line breaks are kept for the output tails. The `baseBranch` fragment in the settings problem, and the base name and git/gh stderr in `/factory-approve`'s fetch and protection messages, go through `cleanText`, so they cannot carry a newline that would forge a line such as "Approved." in the approve or start reply.

The factory's long instruction prompts are not put in the transcript: `submit()` sends a one-line headline as the user message and holds the full text in `instructions`, which the `prompt.compose` hook appends as a `code-factory:instructions` session-scoped system prompt section (hidden from the user, covered by the prompt cache). A plugin's own `prompt.submit` hook never sees its own submissions, so the `context` field of `prompt.submit` cannot be used for this. Work/nudge/release instructions only attach while the loop is live (`autopilot` or armed); the design interview's (which does not arm the guards, so it can commit to the base branch after the person confirms) persist until a successful `/factory-approve` or `/clear`; the next-phase interview's (armed until the person's first reply, see below) end at the first of: a main turn whose answer ends with a line `ROADMAP-DONE` (`isRoadmapDone`; the roadmap prompt tells the model to end the interview's final message with it, both after the person confirmed the items and after "nothing more, stop here"; a faked marker only drops the instructions, the guards do not depend on them), a successful `/factory-approve`, `/clear`, `/factory-start`, `/factory-stop`, `/factory-pause`, a new `/factory-roadmap` (replaced), `ROADMAP_IDLE_MS` (30 minutes) without interview activity (counted from the last main `turn.complete`, answered `AskUserQuestion` call or prompt the person typed; a typed prompt refreshes the clock in `prompt.submit` before `prompt.compose` checks it, so a slow plain-text reply never loses the instructions and idle expiry can only fire on a compose the person did not start), `ROADMAP_MAX_TURNS` (40) completed main turns, or `ROADMAP_CEILING_MS` (4 hours) after launch (`roadmapExpired`, checked in `prompt.compose`). The design interview's instructions are not affected by any of these. Both are lost on a plugin reload or `--resume` (re-run `/factory-design`, which also pauses a running loop first so the design can be committed to the base branch). The section tells subagents to ignore it, but `prompt.compose` carries no agent id, so that is model compliance, not enforcement.

The `Agent` hook handles the independent review: the work prompt tells the model to spawn one fresh agent with `reviewAgentPrompt` verbatim (tagged `[FACTORY-REVIEW-AGENT]`, compared after whitespace normalization, so editing it is denied). The reply must end with `FACTORY-REVIEW: danger=<n> medium=<n> sha=<HEAD>`; the factory parses that (`parseReviewMarker`) into `state.review`, and `isReviewClean` requires 0/0 and a SHA matching HEAD. Review rounds are capped by `maxReviewRounds`. The reviewer usually runs in the background, so the Agent call only returns a launch acknowledgement: the hook stores its `agentId` (from the structured `status: "async_launched"` result; `reviewAgentId`/`reviewAgentAt`, waited on for `settings.reviewTimeoutMs`, default 30 min, capped at 6 h, which is excluded from `decisionsHash` so changing it needs no re-approval; a second spawn and every `SendMessage` except the reviewer's own are denied meanwhile, including during the launch itself (`reviewInFlight` is a synchronous latch around the Agent hook, so parallel spawns and a foreground review are covered, and a reviewer's `turn.complete` that races the state write waits up to 5 s for it), and on timeout the loop pauses instead of nudging), while it is pending nobody but the reviewer may commit, push or edit code outside `.factory/` (so a clean verdict for HEAD cannot cover commits made after the reviewer read the tree; best-effort: only commit/merge/push-class git commands and the Edit/Write tools are covered, not `git rebase/reset/pull/apply`, shell writes or NotebookEdit; the reviewer's own children are denied too; the wait window is frozen into `state.reviewWaitMs` at launch so editing `reviewTimeoutMs` mid-review does not shorten it, and a verdict that arrives after the window or in a session that did not launch the reviewer is dropped), `advance()` does not nudge, and the verdict is read from the reviewer's own final `turn.complete` (`reviewerTurn`/`decideReviewAnswer`): its `agentId` is pinned by the engine, so no other agent can produce it, and text quoted anywhere else is never parsed. A reviewer turn that ends with an `answer` but no verdict is not final (the reviewer may have launched its own background helpers and ended the turn to wait for them; every wake-up is another `turn.complete` with the same `agentId`, confirmed in a live pass), so the factory keeps waiting for a later turn with the marker, and a reviewer that never delivers one pauses the loop at the end of the wait window, counting that as a round (the item is blocked at `maxReviewRounds`). A reviewer turn that ends in an error, abort or refusal frees the loop but counts as a round, so respawns hit `maxReviewRounds` and block the item. The agent's `agentId` proves who spoke, not that it was a real reviewer, so the Agent hook also requires a plain `general-purpose` agent (no custom `subagent_type`, `model`, `name`, `mode`, `team_name` or `isolation`) and Edit/Write on `.claude/agents|commands|skills/` and `.claude/settings*.json` is denied while the loop is live (best-effort: Bash can still write files, and a reviewer reading a repo-controlled `CLAUDE.md` is not defended against). The next-phase interview (`roadmapPrompt`) is armed with these guards only until the person types a reply; that reply disarms them like any typed prompt (an accepted limit, see the next-phase section). The main loop's next turn (the hand-back message) is flagged as the loop's own via `expectReport` whenever the plan is approved, even if the loop was paused meanwhile, so the guards are armed for that turn (`turn.complete` disarms it again when `autopilot` is off). Verified live: the Agent tool's `agentId` equals the `agentId` its `turn.complete` carries.

### Spend ledger (`$.store`)

Costs live outside the repo, in the plugin's own `$.store` (a JSON file under the user's Claude Code config dir, shared by every repo and session, 4 MiB cap), one key per repo: `costs/<owner/name>` (`repoKey` of `git remote get-url origin`, falling back to the working directory's basename). A `RepoCosts` holds the repo total, per-item aggregates (`usd`, tokens per model as `[input, output, cache read, cache write]`, tokens per phase `build|review|ci-fix|design|release|roadmap`, attempts, wall-clock `ms` while the factory drove it, outcome `merged|blocked|skipped`; capped at `MAX_COST_ITEMS`), the last `MAX_RUNS` runs (`/factory-start` opens one), and open marks. Runs and marks are tagged with the working tree that made them (`tree`: the session's absolute `$.session.cwd()`, the same scope as `.factory/lock.json`; `session:<id>` if the cwd cannot be read), because two worktrees or clones of one repo share the ledger key but each runs its own loop. `treeRun` finds this tree's latest run: `liveSpend`, `budgetReached`, the band and `/factory-status` read only that run, `settleCost` charges a mark's dollars to its own tree's run (`mark.tree`, else the caller's), `noteItem(..., { runItemTree })` counts a merge in that tree's run, and `startRun(rc, now, tree)` opens a run for this tree only, so another tree's `/factory-start` never resets this tree's budget and its spend is never counted against it. `keptRuns` keeps the last `MAX_RUNS` runs plus each tree's latest run; both pruning and `normalizeRepoCosts` (every ledger load) use it, so another tree's live run survives any number of runs elsewhere (untagged legacy runs are capped to the last `MAX_RUNS`). Repo totals in `/factory-costs` still sum every run and item. Ledger entries from before the tag load with `tree: ''`: they are summed in the totals but no tree's budget reads them. Non-item spend (design, release, next-phase interview) goes under the `_plan` key, shown as `(plan)`; it does not count toward the run.

Dollars come only from `$.session.usage().cost.usd` (the session's running total; subagents included). A mark `{ key, kind, usd, at }` is stored per session id (`$.session.id()`, remembered in `markOwner` across a `/clear`, which changes the id). `drive()` settles any open mark and opens a new one before each factory `submit()`; `turn.complete` of a factory turn or of the pending reviewer settles the delta into the item and re-marks (`keep`) while the loop is live, while this session's reviewer is still pending (`launchedHere`) or while its hand-back is expected (`expectReport`), otherwise closes the mark. `pause()` (including a budget pause or an unavailable-reviewer pause at the reviewer's own `turn.complete`, where `launchedHere` is already cleared but `expectReport` is set) and `/factory-stop` settle up to now but keep the mark open while a factory turn, this session's reviewer or the reviewer's hand-back is still in flight, so that turn's remaining dollars and tokens are still charged when it completes (the hand-back turn's `turn.complete` then closes the mark because `autopilot` is off and neither a reviewer nor a hand-back is pending); the finished branch, a non-slash prompt the person types (`pause(..., byPerson)`, or a plain settle when the loop is not running) and `session.end` close it at once. A slash command the person types (other than `/factory-*`, which spend nothing) while a mark is open settles the mark up to that moment, keeps it, and sets `personSlash`. The first `turn.start` after that is taken as the slash command's own turn (`slashTurnId`); only when that same turn id completes as a main turn that is not a factory turn does `rebaseMark` move the open mark's baseline to the counter reading at that moment without charging, so the person's slash turn (for example `/compact` during a review wait) falls in the gap. A slash command that runs no model turn (`/cost`, `/model`, `/help`) must not leave the flag armed: it is cleared without a rebase when no `turn.start` arrives within `SLASH_TURN_WAIT_MS` (5 s), when a model-originated prompt (`task-notification`, `peer`) is submitted before the slash turn started, and when a main turn completes before any `turn.start` was seen. A different main turn that completes while the slash turn is still pending is settled into the open mark at once (charged, so the slash turn's rebase cannot wipe it), and a factory turn completing meanwhile does not consume the flag. `turn.start` carries no origin, so this is a best-effort match; every ambiguous case falls on the over-charge side. Only that flag causes a rebase: any other main turn the factory did not start (for example the model's own background `task-notification`) is not rebased, so its spend stays on the open mark and is charged at the next settle. `submit()` clears the flag: if the factory submits its next turn while the person's slash turn is still running, the two turns overlap and cannot be told apart (`isFactoryTurn` is one boolean), so nothing is rebased and the person's turn is charged too; for a budget, over-charging is the safe direction. So the person's own turns are never charged, except in that overlap. Trade-offs: a background reviewer's spend during the person's turn falls in the gap too (under-charged, never over-charged), the mark's `at` is not moved (the item's wall-clock `ms` includes the gap), and it is unverified live whether a `/compact` produces a `turn.complete`; if it does not, its spend is charged to the open mark at the next settle. `costDelta` treats a counter that went backwards (new process, `/clear`) as restarted from zero and charges the new value; a mark older than two days is dropped. When the counter cannot be read and there is no numeric mark, a mark is opened with an unknown baseline (`usd: null`): it attributes tokens and time but never dollars, and the next readable value only sets the baseline, so a resumed session's earlier total is never charged to an item. An unreadable reading never discards a numeric baseline: `settleCost` leaves an existing numeric mark untouched (not deleted, not replaced by the next drive's mark, not closed by a `null` next), and the next readable settle charges the whole span to that mark's item and run; while the counter is unreadable the budget treats spend as unreadable and pauses. Accepted trade-off: if the close was a person's prompt or `session.end` with no reading, the kept mark (two-day TTL) can later charge some of the person's own spend to that item. `settleCost` re-creates a run entry when the ledger has none, so a missing run can never stop the budget from accruing. Tokens come from `turn.complete`'s `usage` while a factory turn runs, reviewer turns (by `agentId`) as `review`, otherwise by the band's stage (`CI`/`merge` is `ci-fix`). All ledger edits go through one promise chain (`editCosts`). Known limits: `editCosts` serializes only within one process (`$.store` has no compare-and-set), so two sessions settling the same repo's ledger at the same instant can lose one update (accepted; unverified against the host store's write semantics); the ledger is not in `.factory/`, so the guards do not protect it from a Bash write to the config dir; this is accepted, so the budget and the spend ledger are advisory against a misbehaving model (unlike `state.json`), and `/factory-costs` says so in its header; the band's stage is in memory, so the phase split after a reload falls back to `build`; per-phase figures are tokens, not dollars.

`/factory-costs [repo-substring|all]` prints the grand total, every repo sorted by spend, and for the current repo (or the matches) the per-item table and the most expensive items; `/factory-costs reset <owner/name>` deletes one repo's ledger and needs the exact key. It is refused while that ledger has an open mark (some session is charging a turn there) or, for this repo, while the loop runs, a factory turn or reviewer is in flight, or another session holds the lock, because it would wipe the run the budget counts.

### Timeline and the person's controls

`advance()`, the Bash hook (only while the loop is live: `commit`, `pr-opened` with number and URL parsed from `gh pr create`'s output, `merged`, `ci-passed`/`ci-failed` from `gh pr checks` output and from the merge gate's `checksVerdict`), the Agent hook (`review-launched`), the review verdict paths (`review-verdict`, `blocked`) and the commands (`resumed`, `paused`, `skip`, `retry`, `release`, `roadmap`) append to `state.events`; identical consecutive events are collapsed. Logging never changes a gate's decision. Commands (registered next to the others; `pause`, `log` and `costs` are `immediate`):

Text the model or the repo controls (commit messages, PR urls, event details, blocked-note reasons, skip notes, pause reasons, todo titles and versions, ledger repo keys and item titles, CI output) can carry terminal escapes, so it is cleaned with `stripControls`/`cleanText`/`safeLines` (lib.ts: C0 controls, tab and newline become a space, DEL, C1, U+00AD, U+061C, U+180E, zero-width U+200B-U+200F and U+2060-U+2064, bidi U+202A-U+202E and U+2066-U+2069, U+FEFF are removed) both when it is stored (`appendEvent`, `sanitizeEvents`, `commitMessage`, `parsePrUrl`, `parseItemArg`, the ledger's item titles, `pause()`'s reason, `blockedNotes`) and when it is printed (`formatLog`, `statusReport`, `costsReport`, `buildView`/`shortEvent` for the band, the `toast`/`status` wrappers around `$.ui.toast`/`$.ui.status`, command replies that echo repo text such as `/factory-approve`'s queue and settings problems, and `submit()`'s transcript headline). Command handlers must stay function literals, so replies are wrapped one by one with `safeLines`; a new reply that echoes repo or model text needs the same.

- `/factory-status`: `statusReport`: state, current item with stage, attempt n/max, review round n/max, PR, elapsed time and spend, run spend against the budget, the queue, blocked items with the first line of their note, recent events, all items.
- `/factory-log [ID]`: the timeline, oldest first, with the gap since the previous event.
- Item ids for `log`, `skip` and `retry` go through `parseItemArg`: `[A-Za-z]{1,10}-\d{1,6}` followed by whitespace or the end, input over 2000 characters refused, so `../x`, `--help` or `T-001/../..` are rejected with a usage line before any file or process is touched.
- `/factory-pause`: `pause()` (cost settled, lock released) but, unlike `/factory-stop`, keeps `expectReport`, so a pending review's hand-back is still read; the item, attempts and review rounds stay.
- `/factory-skip <ID> [reason]`: writes `.factory/blocked/<ID>.md`; the loop drops the item as current and moves on after the running turn.
- `/factory-retry <ID>`: refused while another session holds the lock, while the approval hash does not match, for a `proposed` or effectively `done` item; otherwise removes the blocked note (`rm -f` through `process.run`, since `$.fs` has no delete) and resets `attempts`/`reviewRounds` if it is the current item. It never touches `todo.md`, so it cannot flip `done` or change decisions.

### Next phase

`roadmapPrompt` (lib.ts) summarizes the done items, merged ids and the per-item spend (`costSummaryForPrompt`), then has the model interview the person with AskUserQuestion about goals, versions and where to stop, the items in priority order and each item's how/accept/tests, accept "nothing more, stop here" (then change nothing), otherwise append `proposed` items with ids continuing from `nextItemId` and update `design.md` (and `settings.json` only where decided), ask the person to confirm, and end by giving the person the `designPushSteps` lines (`#` comments and `&&`-chained command lines; none if `baseBranch` is unsafe) to commit and push the three design files to the base branch themselves, then `/factory-approve` and `/factory-start`. It tells the model not to commit, push, stage, branch or open a PR, and not to run those commands itself. It is submitted with `isDesign = true` and a launch time (instructions persist across the person's answers but expire on the triggers listed above: the `ROADMAP-DONE` line, approve, `/clear`, start, stop, pause, a new roadmap, 30 idle minutes, 40 turns or 4 hours) and `guarded = true`, so it is *armed* whether the loop launched it or the person ran `/factory-roadmap`: every loop guard applies (no commit or push on the base branch, no force push, no `gh api` writes or merges, no Edit/Write under `.claude/`), while edits to `.factory/todo.md`/`design.md` stay allowed. The guards are disarmed when that turn ends (`autopilot` is off), on the person's next prompt, or when the turn outlives the 3 h limit. Accepted limit: the interview needs the person's answers, so its first typed reply disarms the guards, and from then on the model is in a person-driven conversation at the same trust level as the `/factory-design` interview (it could commit to the base branch if the person lets it); only the unattended stretch, the auto-launched turn before anyone answers, stays armed. `roadmapAsked` is written before it is submitted and reset only by a successful `/factory-approve`, so `turn.complete` and the watchdog cannot ask twice. `/factory-roadmap` asks at any time the plan is approved, nothing is runnable (`pickNext` empty, no current item) and no other session holds the lock; it pauses a running loop first. It is refused while a factory turn is in flight (`turnBusy`, for example a release turn whose instructions it would replace), while `advance()` runs, or while its own launch is pending (`roadmapPending`, set before the 300 ms launch timer and cleared when the launch finishes), so two quick invocations start one interview.

### Settings

`parseSettings` is the schema (defaults in `DEFAULT_SETTINGS`); a present but malformed `buildCmd`, `e2eCmd` or `e2eFor` is a settings problem (it is never silently dropped); `testCmd` must be a non-empty argv array and each configured command is capped at 10 minutes. Adding a setting means updating the `Settings` type, `DEFAULT_SETTINGS`, `parseSettings`, and the JSON example inside `DESIGN_PROMPT`. Settings are part of the approval hash, so changing any of them invalidates a prior approval.

- `budgetUsd` (number, default 0 = off; negative or non-numeric is a settings problem): the loop pauses once this run's spend reaches it, checked in `advance()` and after a factory or reviewer `turn.complete` (`budgetProblem`); it never interrupts a turn. It fails closed: when it is set and this run's spend cannot be read (no `cost` from the session, the store unreadable, or the last ledger write failed, tracked in `costFailed`) the loop pauses with `budgetUnreadableReason`, and `/factory-status` says the budget cannot be enforced. The check right after a factory or reviewer `turn.complete` (`stopForBudget`) tolerates one such miss in a row (`unreadableMisses`, reset by any readable read); `advance()` never does. A run starts at `/factory-start`, so `/factory-start` after a budget pause begins a fresh run.
- `askNextPhase` (boolean, default true): ask for the next phase when the plan is fully done.

Both are in the approval hash, but only when they differ from their defaults (`decisionsHash` leaves defaults out), so plans approved before these settings existed keep their hash.
